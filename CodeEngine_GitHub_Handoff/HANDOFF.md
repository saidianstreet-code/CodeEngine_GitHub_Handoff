# CodeEngine — HANDOFF для продолжения разработки

> **Назначение:** этот файл — краткая передача контекста между чатами ChatGPT. Перед продолжением работы новый чат должен сначала прочитать этот файл, затем изучить актуальные исходники проекта, которые пользователь загрузит в чат или которые находятся в репозитории.

## 1. Проект

- **Название:** CodeEngine
- **Язык / UI:** Java + Swing
- **Платформа разработки:** Windows
- **Рабочая папка:** `C:\CodeEngine`
- **Основная цель:** собственный игровой движок с редактором сцен, возможностью создавать 2D-игры и в перспективе полноценные 3D-игры, а также поддержкой Java-скриптов.
- **Предпочтительный стиль разработки:** пошагово, небольшими этапами; после каждого этапа пользователь компилирует и проверяет проект. Не выдавать весь движок целиком за один раз. Когда изменения сложно применить вручную, предоставлять полный исправленный файл.
- **Язык общения:** русский.

## 2. Как продолжать работу

1. Прочитать этот `HANDOFF.md` целиком.
2. Проверить актуальные исходники, которые пользователь приложит к сообщению (они важнее любых описаний в этом файле, если расходятся с ними).
3. Не предполагать, что старые фрагменты кода всё ещё совпадают с файлами пользователя.
4. Вносить изменения по одному понятному этапу и объяснять, какие файлы заменять.
5. После каждого этапа попросить пользователя выполнить компиляцию и сообщить полный текст ошибок, если они появятся.
6. При завершении этапа обновить `HANDOFF.md` и `CHANGELOG.md`: записать, что изменено, что проверено и что осталось сделать.
7. Не заявлять, что GitHub-репозиторий обновлён, если пользователь не подтвердил загрузку или инструмент действительно не выполнил её.

## 3. Сборка и запуск

Из корня проекта `C:\CodeEngine`:

```bat
javac -d out src\codeengine\*.java src\Main.java
java -cp out Main
```

Если структура исходников изменилась, сначала проверить реальные пути и скорректировать команду. При ошибке сохранять полный текст сообщения компилятора, включая имя файла и номер строки.

## 4. Текущий этап на момент подготовки handoff

**Этап: удобный Inspector и минималистичный выбор компонентов.**

Последняя обсуждавшаяся задача: улучшить выбор компонентов в Inspector, чтобы пользователь мог находить и добавлять компоненты удобнее, а интерфейс выглядел минималистично.

В текущем контексте подготовлен полный файл `InspectorPanel.java`, который:
- сохраняет редактирование координат и размеров объекта;
- поддерживает добавление и удаление компонентов;
- добавляет диалог выбора компонентов с поиском и краткими описаниями;
- содержит обработку `ColorRenderer`, `SpriteRenderer`, `Rigidbody2D` и `BoxCollider2D`;
- сохраняет настройки рендереров и физики, включение/отключение компонентов и перетаскивание изображений из файловой панели.

**Важно:** файл был подготовлен, но полная компиляция всего проекта после его замены не подтверждена. Поэтому следующий шаг — сверить этот файл с реальным проектом, заменить `src\codeengine\InspectorPanel.java`, выполнить сборку и исправить ошибки, если они будут.

Файл `InspectorPanel.java` должен быть приложен пользователем отдельно или взят из актуального состояния проекта. Не считать его присутствующим в GitHub, пока пользователь не подтвердит загрузку.

## 5. Известные особенности и предыдущие ошибки

Во время разработки ранее возникали ошибки, связанные с:
- обращением к экземплярным массивам `buttons`, `pressed`, `released` из статических методов в `Mouse.java`;
- ссылкой `Editor.java` на `Main`, когда класс не находился компилятором;
- несовпадающей сигнатурой `Entity.update`;
- отсутствующими методами `Transform.setX/Y`;
- отсутствующим импортом `codeengine.SpriteRenderer`;
- неверным импортом `javax.xml.crypto.dsig.Transform` вместо собственного `codeengine.Transform`;
- тем, что Inspector показывал не тот выбранный объект (исправлялось);
- тем, что Inspector сначала не показывал компоненты — нужно проверить ожидаемое поведение на актуальных исходниках.

Это история прошлых проблем, а не утверждение, что все они присутствуют сейчас.

## 6. Основные цели редактора

Планируемые возможности, которые обсуждались:
- панель Hierarchy со списком объектов сцены;
- Viewport / Game View;
- Inspector для редактирования объекта и его компонентов;
- нижняя панель файлов проекта;
- добавление компонентов и настройка их свойств;
- `Mouse.java` с обработкой кликов и позиции курсора;
- кнопка Play и отдельный режим запуска игры;
- в дальнейшем — клонирование состояния сцены перед Play Mode, чтобы игровые изменения не портили редакторскую сцену.

Не считать каждый пункт уже реализованным: сверять по исходникам и фактической проверке.

## 7. Как вести журнал

После каждого подтверждённого этапа добавлять запись в `CHANGELOG.md`:
- дата;
- что изменено;
- какие файлы затронуты;
- результат компиляции;
- результат ручной проверки;
- известные проблемы и следующий шаг.

Различать статусы:
- **Сделано** — код изменён;
- **Скомпилировано** — компилятор завершился без ошибок;
- **Проверено** — пользователь подтвердил работу функции.
